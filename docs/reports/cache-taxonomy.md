# 缓存层次澄清：前缀缓存 vs 语义复用（两种缓存，叠加而非替代）

> 背景问题："Reasonix 用前缀优化不是有 99%+ 缓存命中吗？用它保底不行吗？"
> 一句话答案：**那是两种不同的缓存，Reasonix 的 99%+ 是会话内的前缀缓存
> （省单价），我们的命中率是跨会话的语义复用（省数量）——它们不冲突，
> 而是相乘叠加。Reasonix 保不了我们的底（跨会话空白它不覆盖），
> 但我们保它的底（检索失败时零副作用）。**

## 两种缓存的本质区别

| | Reasonix 前缀缓存（provider KV cache） | semantix 语义复用（L2/L3 切片缓存） |
|---|---|---|
| **缓存什么** | 已发过的那段 prompt 的 KV 状态 | 历史会话中提取的知识切片（偏好/流程/经验） |
| **命中条件** | 字节级前缀重复（同一会话内连续 turn） | 语义检索（新任务 vs 历史切片相似度） |
| **作用域** | **会话内**（跨会话不共享！） | **跨会话**（用户级库 ~/.semantix/user.db） |
| **省什么** | 每 token 单价（$0.27/M → $0.07/M，重复计算） | token 数量（模型不用重新思考/执行重复工作） |
| **命中率** | 可达 99%+（前缀稳定时，纯字节匹配） | 取决于检索质量（M0-2 门槛 ≥70%） |
| **回答的问题** | "这段 prompt 我见过吗？"（传输/计算） | "这个任务以前做过吗？该带什么历史？"（知识） |
| **决定者** | 模型服务商基础设施 | 我们的算法 |

**关键事实**：前缀缓存**无法跨会话工作**——新会话的 prompt 从零开始，历史会话的前缀早已不在缓存里。Reasonix 的 99%+ 说的是**同一会话内**每轮重发历史时的重复计算命中。"跨会话记忆"这个空白，前缀缓存**天然不覆盖**——这正是我们要填的位置。

## 叠加模型（成本公式）

```
总成本 = Σ token数 × 单价

前缀缓存 影响：单价（cache hit 价 ≈ miss 价的 1/4）
语义复用 影响：token 数（注入历史 → 模型少生成/少探索）

总成本 = (1 - 复用率) × token数 × (miss价 或 hit价)
             ↑我们                ↑Reasonix
```

**关键设计**：我们的注入块位置固定（system prompt 末尾、用户消息之前）
→ 前缀稳定 → **注入块本身也吃前缀缓存** → 注入的额外成本 ≈ 0（cache hit 价）。
所以两者是**乘法叠加**，不是二选一：

- 只有 Reasonix：每轮省 75% 单价，但重复工作照做（token 数不变）
- 只有我们：跨会话省 token 数，但注入成本按 miss 价计
- **两者都有**：注入块 ≈ 0 成本 + 复用省 token —— 演示实测节省 79.8%

## "保底"框架（诚实版）

| 问题 | 结论 |
|---|---|
| Reasonix 的 99%+ 能保我们的命中率吗？ | **不能**。它是会话内字节匹配，我们是跨会话语义匹配，互不覆盖 |
| 我们检索失败（0% 命中）会拖累 Reasonix 吗？ | **不会**。注入块为空 → 行为与基线完全一致 → 前缀缓存照常工作。**我们保它的底** |
| 真正的保底是什么？ | M0-Gate 分级：命中率 <70% → 先降级验证（提取粒度调整）；两轮不过 → 止损，保留的资产是注入/验证/观测框架（它们与检索算法解耦） |
| 我们的命中率目标 vs 前缀缓存目标 | 前缀 99%+（字节）≠ 语义 70%+（相似）。语义 70% 已是很高的复用率（垂类重复任务场景）——且即便 grey/miss 也有 waste++ 观测兜底 |

## 结论

1. **给客户讲**：我们的注入块**配合**他们的前缀缓存（固定位置 → 双缓存叠加），
   不是替代；跨会话记忆是前缀缓存覆盖不到的地方，我们填上。
2. **给团队讲**：把"前缀命中率"当作**已就位的基础设施假设**（免费、会话内、字节级），
   把我们的"语义命中率"当作**要验证的产品假设**（付费、跨会话、语义级）。
3. **保底策略**：机制层（注入/验证/观测/安全/安装）已全部闭环且与算法解耦；
   算法层（BM25/hash-embedding）是最短板，也是唯一未用真实数据验证的部分
   ——这就是为什么 `verify` 是当前最高优先级动作。

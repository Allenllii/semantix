# SWE-lite36 提分循环（Score Loop）规格

> 状态：执行中（2026-09-28 启动）
>
> 跟踪 Issue：待建（Gnosil/semantix）
>
> 约束：**不改变 agent/kernel 架构**；每轮小样本（≤12 题）；每步 commit、issue 跟踪、draft PR 沉淀；不跑全量 36 题除非收尾判定。

## 1. 背景与证据基线

R2 复跑（issue #508，2026-09-27）终表：off 11/35、strict 12/35、ctx4096（产品默认）14/33。对 off 臂 25 个失败的全量解剖（trajectory + agent-output + grading 复核）得出失败分类：

| 类别 | 数量 | 证据 | 性质 |
|---|---:|---|---|
| 开局 429 零烧 | 6 | steps=0、agent-output 尾部 `status 429 code 1302` | **基础设施** |
| 中途 429 击杀 | 4 | 7746/5221/5413/8906，retries 耗尽（10 次退避封顶 15s ≈ 2.5min）后死 | **基础设施** |
| 15min 墙钟超时 | 5 | 11283（9.8KB patch 被杀）、11564/5103/5495/9359 | 限额+求解混合 |
| 输出限制三振 | 2 | 14182/11019，`hit the output limit 3 times without tool progress` | 模型行为 |
| max-steps(40) 到顶 | 1 | 8365，patch 4.2KB 且自称"complete and verified" | 限额 |
| 真实求解错误 | ~7 | 6116/7373/8906 等：patch 语义接近但差最后一档（如 8906 差一条错误消息字符串断言） | 模型能力 |

**核心发现：25 个失败里 10 个（40%）是 429 限流毒杀，不是模型失败。** 产品重试（`harness/provider/retry.go`）MaxRetries=10、退避封顶 15s、Retry-After 上限 60s，总耐心 ≈2.5min；bigmodel coding-plan 的限流窗口明显长于该值。当前缓存命中率 82%、bash 失败率 41%（多为开发期测试失败，属正常）。

## 2. 循环协议（每轮固定）

1. **假设**：从失败解剖提出一个可证伪假设，写明预期翻转的任务集合与数量。
2. **改动**：最小实现（产品代码或 runner 配置），gofmt + 定向测试。
3. **小样本验证**：只重跑假设命中的任务（≤12 题）+ 必要的对照；不跑全量。
4. **判定**：翻转数 > 0 且无回归（原本 resolved 的任务保持 resolved）→ 假设成立，改动保留；否则 revert 并记录。
5. **沉淀**：commit（每逻辑步一个）→ issue 评论 → draft PR 更新。
6. **收尾**：≥3 轮或增益停滞时，跑一次 36 题全量确认（需用户批准 API 花费）。

经济性护栏：单轮重跑 ≤12 题 ≈ ≤1.5h wall、≈≤0.6M prompt tokens/题，与 R2 单题均值持平；墙钟/步数限额不动（保持与 R2 可比）。

## 3. 轮次

### I1 — 429 耐性（预计最大增益 +2~4 题）

- **假设**：把 429 的重试耐心从「10 次 × ≤15s」扩到 429 专属预算（20 次、Retry-After 上限放宽、无 Retry-After 时指数退避封顶 60s），配合 runner 串行化（api_concurrency=1），被限流毒杀的任务可存活至窗口解除。
- **改动面**：`harness/provider/retry.go`（429 分支）、`retry_test.go`；runner 侧 campaign 副本 `api_concurrency=1`（不入库，issue 记录）。
- **验证集**：ctx4096 配置下重跑 429 受害者（零烧 4 + 中途击杀若干，以 ctx 臂实际名单为准，≤10 题）。
- **判定**：任一受害者 resolved = 翻转；全部保持 unresolved = 假设不成立，revert。
- **风险**：长等待吃 900s 墙钟预算——退避总额须 ≤6min，超出即放弃该任务（与现状等价的失败，不比现状差）。

### I2 — 输出限制生存（候选）

- **假设**：`maxEmptyFinalBlocks` 3→5 + 更尖锐的续写 nudge（"先用工具做最小编辑，不要重复分析"），14182/11019 类长推理任务可活过三振。
- **验证集**：仅 14182/11019 两题（+ I1 中命中该 guard 的新增者）。

### I3 — 近失精确度（候选，探索性）

- **假设**：8906 型近失（差一条测试断言的错误消息字符串）可用记忆卡质量解决——distill 的 Context 卡包含"测试断言精确字符串/契约"的提取模板。
- **验证集**：8906/7373/6116 三题。
- **风险**：改动面在 kernel/slice distill 模板，影响所有卡；先离线评估新模板对既有库的扰动再上。

### I4 — 限额头部空间（候选，需用户单独批准）

- max_steps 40→60 / agent_seconds 900→1200：直接成本上升（token/时长），只对超时三人组（11283/5103/5495）测试。

## 4. 回退

每轮独立 commit；不成立即 `git revert` 对应提交。runner 配置改动不入库，天然可回退。

## 5. 诚实边界

- 小样本翻转 ≠ 全量提升：I1/I2 翻转若达 +2 以上，收尾全量确认后再宣称。
- 429 耐性改善对真实用户同样有价值（长任务穿越限流窗口），但过耐 = 用户侧长等待；退避总额上限是产品取舍，spec 内明确（≤6min）。
- 记忆系统在本 loop 中不是主角：I1/I2 与记忆无关，I3 才触及。若 I3 离线评估显示模板扰动过大，记忆侧改进转回 #508 后续，不阻塞提分。
